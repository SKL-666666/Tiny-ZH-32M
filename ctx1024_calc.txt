31.5M 参数: 31.47M
64M  参数: 64.21M

========================================================================
核心洞察：训练成本按 token 计，不按 sequence 计
========================================================================
配置                           micro_bs  accum   seq   tok/step
------------------------------------------------------------------------
现在 seq256                          64      2   256     32,768
原生 seq1024                         16      2  1024     32,768
原生 seq1024 (bs32)                  32      1  1024     32,768

结论：seq 从 256→1024，batch 从 64→16 即可保持 tok/step 不变
     → 训练时间几乎不变（同样 token 数）
     → 显存占用也几乎不变（bs×seq 乘积相同）

========================================================================
显存：激活值对比（bs×seq 相同，但注意力矩阵是 O(seq²)）
========================================================================
  seq= 256 bs=64: 材料化注意力      101 MB, SDPA 实际约      13 MB
  seq=1024 bs=16: 材料化注意力      403 MB, SDPA 实际约      50 MB

  → 1024 的注意力矩阵物理上大 4 倍，但 SDPA 不存，实际增量可忽略

========================================================================
算力：注意力部分的 FLOPs 占比
========================================================================
  seq= 256: 注意力    7.1M FLOP/tok, 占总量   1.8%
  seq=1024: 注意力   28.3M FLOP/tok, 占总量   7.3%
  seq=2048: 注意力   56.6M FLOP/tok, 占总量  14.7%

  → seq 1024 时注意力只占 7.9%，总训练时间增加约 7%

========================================================================
真正需要改的东西
========================================================================
  1. config.py: max_position_embeddings 512 → 1024
  2. 训练脚本:  --seq-len 256 → 1024
  3. rope_theta: 10000 → 500000（长上下文更稳）
  4. GGUF 导出: 会自动读 config，无需改

  数据侧：预训练不用改（token 流是连续的，1024 窗口跨文档没关系）
         SFT 要注意（对话样本短于 1024 会大量 padding，浪费算力）

========================================================================
数据量需求
========================================================================
  seq 1024 × 16 bs × 2 accum = 32,768 tok/step（和现在一样）
  跑 7000 步 = 2.29 亿 token
  以 45k tok/s 计 = 1.4 小时
